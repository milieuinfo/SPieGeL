    Open questions¶

    Questions that the analysis could not settle. When one is answered, record the answer as an ADR and link it here, rather than deleting the question.

    Product and scope¶

    1. One multi-tenant service, or one service per domain? SPieGeL's design assumes one stateless multi-tenant service (FR-MT-01). Newer domains, however, use small purpose-built services. Which model does the organisation want for the long term?
    2. Are the non-public access levels still used? The X-Cite project assumes authentication is "no longer used in practice". If that is true for every domain, phase 2 can drop access control. Usage data per domain should settle this before FR-AC-01 to 03 are built.
    3. Are reconciliation, Linked Data Fragments and the alternative search back ends used by anyone? They exist in the predecessor but are not routed.
    4. Is keyword search still needed? The X-Cite project grades full-text search as won't; the predecessor offers it per domain.
    5. Should the restricted HTML view of incoming relations exist? The predecessor intended it but never had it in effect (see Request flows).
    6. Is the dba domain still maintained, or can it be published as a static snapshot? Answered: the domain is fully static. It can be published from a read-only snapshot, without a store that is loaded continuously (see question 29).
    7. Which consumers rely on the predecessor's URIs and formats? For example dataset catalogues and metadata portals that link to it.

    Front end¶

    1. Do the omgeving-ld browser components stay? Answered by ADR 0005: no. They are replaced by Flux components where those exist (accordion, rich data table, pager, map, properties), and by new components built to Flux's conventions where they do not: the hierarchy tree, incoming relations, the collection table and the SPARQL editor (FR-HTML-05; see Design system: Flux). Still open: must the same-origin /sparql and the HTML conventions in Client components (ld-subject, the .rq templates under /queries/) stay for a transition period, for pages elsewhere that still embed the old components?
    2. Which template engine for HTML? The design system is decided: Flux (ADR 0005). The template engine must emit custom elements, slots and attributes cleanly, and encode output by context (NFR-SEC-05). It must also work without Spring, because spiegel-adapter-html has no Spring dependency (ADR 0004), and support translation files (FR-HTML-12) and reusable fragments, such as the RDF term. FreeMarker and Pebble do not encode by context, which leaves Thymeleaf (templates loaded at run time) and JTE (templates compiled, type-safe). Which of the two fits depends on whether tenants write templates of their own or configure their layout (FR-HTML-03). On hold: the question waits for question 40, because a page built in the browser needs no template engine on the server.
    3. Where are the domain-specific explorer scripts for imjv, cbb and dba, and are they still needed?
    4. How are presentation rules expressed? The predecessor chooses blocks and components with XSLT rules by type and predicate (see Data-dependent HTML rendering). FR-HTML-06 makes these rules configuration. Candidates: rules attached to profiles (as in Prez), viewers per URI template (as in ELDA), or a small rule format of our own.
    5. Under which licence is Flux published, and can external contributors build SPieGeL? The Flux repository has no licence file, and its packages come from the department's Artifactory, not from the public npm registry. SPieGeL is public and MIT-licensed, and its release would bundle Flux code (see Design system: Flux).
    6. Do the new Linked Data components live in SPieGeL or in Flux? A resource description, a hierarchy tree, incoming relations, a collection table, a geometry map and a SPARQL editor are needed (see Design system: Flux). Contributing them to Flux makes them reusable but ties their release to Flux's. Answered by ADR 0014: what is specific to Linked Data stays in SPieGeL; what turns out to be generic, such as paging on the server or WKT input for the map, is offered to Flux. The hierarchy waits for question 39.
    7. Do interactive components query /sparql from the browser, or call small JSON endpoints? The predecessor's components build SPARQL in the browser. Server-side endpoints per function keep queries configurable, cacheable and authorised (NFR-SEC-03, NFR-SEC-04). A map of a resource's own geometries needs neither, because its data is in the page. The Flux team assumes that long lists of incoming relations are paged like the RDF, as paged lists with their own URI; FR-RA-07 only covers the subject's own properties, so that is to be decided here as well. A map of many resources (for example all members of a collection) does need a follow-up request. With /sparql, the GeoSPARQL 1.1 function geof:asGeoJSON could return GeoJSON directly, but support differs between stores and its output is always WGS84. Answered by ADR 0015: neither. The components request paged lists, which are Linked Data resources with their own URI (?_property=…, ?_inverse=…), as JSON-LD with a fixed @context; the queries stay on the server, cached and authorised.
    8. Where does the portal discover domains? From the tenant configuration (always complete for SPieGeL's own tenants, but blind to domains published elsewhere), or from the actual publication, for example a dcat:Catalog per domain in the umbrella open data catalogue (always in step with what is published, but it requires that catalogue to describe every domain), or both (FR-HTML-08). And which properties describe a domain in the catalogue: title, description, host name, SPARQL endpoint?
    9. Which languages does the interface offer? Dutch only, Dutch and English, or also French and German (FR-HTML-12)? Do Flux and Digitaal Vlaanderen's global header support the same languages, and who maintains the translations?

    10. Do we adopt, fork or build the SPARQL editor? @sib-swiss/sparql-editor (MIT) is a web component built on YASGUI that autocompletes classes and properties from an endpoint's VoID description, lists its SHACL example queries and reads its prefixes from sh:prefix, all metadata that SPieGeL publishes (FR-META-03, FR-SPARQL-04). See UniProt. Adopting it would save building the editor, the component with the least Flux support (see Design system). Points to check before choosing:

      • Content Security Policy: whether the component and the editor library it uses work without inline scripts and inline styles (NFR-UI-03).
      • House style and accessibility: whether its look can follow Flux, and whether it meets the accessibility guidelines that come with Flux (NFR-UI-01, NFR-UI-02).
      • Results: whether it shows results itself, or SPieGeL renders them with clickable IRIs and labels in vl-rich-data-table (FR-SPARQL-03, FR-HTML-10).
      • Languages: whether its interface texts can be translated into Dutch (FR-HTML-12, question 27).
      • Load on the endpoint: its autocompletion queries /sparql from the browser. They count towards the rate limits (NFR-OPS-08), and relate to question 24.

      • Build and supply: whether it is bundled in SPieGeL's own front-end build rather than loaded from a CDN, and how much it depends on one small team at SIB.

      • Keyboard: a code editor uses Tab for indenting, so keyboard users need a documented way out of it (WCAG 2.1.2, raised by the Flux team).

      The options are to use it as it is, to fork it with Flux styling, or to build an editor on YASGUI or another editor library directly.

    11. Does the predecessor's "Browse dataset" tree work? The XSLT renders <ld-dataset> for catalogues and datasets, but omgeving-ld 1.7.27 does not register the component and its bundles do not contain it (see Client components). A check on a live catalogue page settles whether users have this tree today, which matters for the migration (see question 7), not for SPieGeL's requirement (FR-HTML-05).

    12. How are data structures made visible? Flux 2.21.0 offers vl-cascader, a drilldown with a breadcrumb that loads each level on demand, as a base for the hierarchies of concept schemes and catalogues (FR-HTML-05). Rather than choosing between a drilldown and an expanded tree now, the Flux team has been asked to think about how data structures in general can be made visible: hierarchies, collections, and perhaps the structure of a domain's data (FR-HTML-15). Until it answers, vl-cascader is the candidate (see Design system: Flux, ADR 0014).

    13. Is HTML rendered on the server, or built in the browser by a JavaScript one-page application? The Flux team suggested a one-page application instead of server-side templates, and is investigating whether it is possible and desirable, given how much logic it moves into JavaScript. The analysis so far assumes rendering on the server, with Flux components that upgrade in the browser (Design system: Flux, constraint 2). The investigation should answer how a one-page application meets what is already decided:

      • NFR-UI-04: the title, properties, links and alternate formats are readable without JavaScript. The analysis ruled out data.vlaanderen.be's approach for this reason (Design system: Flux).
      • ADR 0007: subject pages are the landing pages for links from GIS layers, downloads and APIs, and must work at once for people, crawlers, link previews and web archives.
      • FR-HTML-04: the subject IRI, <link rel="alternate"> and the embedded JSON-LD are in the HTML as sent.
      • ADR 0014: the resource description and the RDF term are templates on the server. In a one-page application they become components, so seven components instead of three or four.
      • NFR-PERF-01: a description from the cache within 50 ms on the server. In a one-page application the visitor also waits for the bundle and a second request for the data.
      • ADR 0019: search engines index reliably what is in the HTML as sent: the schema.org block, Open Graph tags and canonical links (FR-HTML-16, FR-HTML-17).
      • Rendering on the server with Lit needs Node.js, a second runtime next to the Java server.

      What a one-page application would gain: no templating in Java, one code base in the Flux team's own stack, richer interaction, and a server that only serves RDF and JSON-LD, which fits the paged lists of ADR 0015. A middle way keeps the content rendered on the server and moves more of the interaction into JavaScript components. Question 9 waits for this answer.

    URI policy¶

    1. Where does the list of valid concepts per domain come from? In the predecessor it is deployment configuration. Options: SPieGeL's tenant configuration, the data itself (co:Collection resources), or the vocabulary projects. Answered by ADR 0012: from the data. Template variables are typed by a pattern; a value that matches is looked up, and a negative result is cached per data version. A tenant that wants a closed list writes it as a pattern.

    Architecture and operations¶

    1. Which edge concerns move into SPieGeL? The 303 redirect, CORS, HSTS and input filtering are currently handled by the reverse proxy. Rate limiting (NFR-OPS-08) is a new concern for the same choice. At the edge it protects SPieGeL before any work is done, but it only knows addresses. That is enough for public access, which is unauthenticated, but not for limits per authenticated client. In SPieGeL it can also limit per authenticated client, per tenant and per kind of request, but it needs a counter shared between nodes. See Request flow.
    2. Does the core use Jena's model types, or its own RDF abstraction? See Hexagonal design. Answered by ADR 0010: the core uses Jena's graph types from jena-core, and nothing from jena-arq.
    3. Is the data loading (ETL) chain in scope of this project at all, or a separate line of work?
    4. Which configuration mechanism in production? For example environment variables, mounted files or a configuration server. Answered by ADR 0013: a versioned artefact built from one central configuration repository, validated in CI, mounted read-only and rolled out with a rolling restart; credentials come from the platform's secret store.
    5. Fork pull requests: the internal CI does not build pull requests from external forks. When external contributors appear, do we add a minimal public CI for them?
    6. Are redirects for moved or retired URIs data or configuration? Trifid reads them from the store, modelled with the W3C HTTP vocabulary, so data owners can manage them without a deployment (see Trifid code review). The alternative is SPieGeL's tenant configuration. This affects NFR-OPEN-02. Partly answered by FR-URI-11: both, by scale. A single URI is data in the store, a whole URI pattern or host name is configuration. The data describes the fact (dct:isReplacedBy, a status, a tombstone) rather than the HTTP response, because the HTTP in RDF vocabulary is a W3C note that is no longer maintained, and the fact is also useful to RDF consumers. Still open: the exact properties for a tombstone, and whether the domains' existing validity properties are enough for FR-URI-09.
    7. Hand-written queries, generated queries, or both? Prez generates each description query from a SHACL shape per profile; SPieGeL's requirements assume query files (FR-RA-02). Generating the simple cases and keeping files for tuned ones is a possible middle way (see Prez code review). Answered by ADR 0012: default .rq templates shipped with SPieGeL, replaced or extended by hand-written files. Generation from SHACL may come later, as an adapter that supplies QuerySpecs.
    8. Do we adopt the Linked Data API vocabulary for tenant configuration? ELDA's model (item and list endpoints, item templates, selectors, viewers, formatters) covers most of FR-URI-01, FR-RA-01 and FR-HTML-03, and comes with a published vocabulary (see ELDA code review). The alternatives are a subset of it, extended with profiles and access levels, or SPieGeL's own format. Answered by ADR 0012: no. The configuration is Turtle in SPieGeL's own small vocabulary, which reuses api:uriTemplate and api:itemTemplate along with prof:, sh:, dcat: and void: terms.
    9. Where do the labels of external vocabularies come from? Either every store holds the external ontologies its data uses, which is simple for SPieGeL but means loading and maintaining the same ontologies in every store (a job for the loading chain, question 15). Or SPieGeL has one shared vocabulary source for all tenants, as Prez bundles labels of common vocabularies (Prez code review), which loads each ontology once. Or both, in that order (FR-HTML-11). A fourth option, fetching an unknown vocabulary from the web while a request is handled, is ruled out: it is slow, depends on third-party sites being up, and conflicts with NFR-SEC-06 (SPieGeL only contacts configured sources). Loading vocabularies from the web ahead of time, into the shared source, remains possible as part of maintaining it. Answered by ADR 0021: the domain's own store first, then extracts of external vocabularies in the configuration: only kinds, labels and descriptions, refreshed ahead of time by a CI job and reviewed. Labels of resources of other domains are question 42.

    10. Materialise or translate non-RDF sources (FR-DS-02)? Answered by ADR 0009: relational sources that must be current are translated per request by Ontop, running as a separate SPARQL endpoint; everything else is materialised with RML in the loading chain. Still open: which sources need to be current to the second. The analysis that led to the decision follows. With materialisation, an RML processor (for example RMLMapper or RMLStreamer) generates RDF into a store in the loading chain (question 15). SPieGeL then only reads that store through its SPARQL adapter, and needs no extra adapter. With translation per request (a virtual knowledge graph), queries are rewritten against the source itself, so data is always current, but tool support is narrower: as far as we know it exists mainly for R2RML over relational databases (for example Ontop, which can itself expose a SPARQL endpoint). RML covers more source types (CSV, JSON, XML, Web APIs), but every RML processor we looked at (October 2026) materialises; none rewrites queries per request:

      • RMLMapper (Java 21, MIT, used as a command-line tool or a library) reads relational databases through JDBC. Its database access (the dataio library) only accepts a fixed list of databases (MySQL, PostgreSQL, SQL Server, Oracle, IBM DB2, H2, Denodo, Athena, Snowflake). Trino is not on it, so Trino would need a change to that library. It also loads the whole query result into memory as CSV before mapping it. It depends on both Jena and RDF4J, and its support for the Community Group's RML modules is still partial.
      • RMLStreamer (Apache Flink) reads JDBC, Kafka and TCP streams, but its last release dates from 2023.
      • CARML (Java, RDF4J, Project Reactor) has no relational source at all: only CSV, JSON and XML.
      • Morph-KGC (Python) covers the most databases, through SQLAlchemy rather than JDBC, and already supports RML 1.2. It can only run as a separate step in the loading chain, not inside SPieGeL.

      So translation per request means R2RML and a tool such as Ontop; RML in practice means materialisation. Which sources need to be current to the second, and which can be loaded periodically? 29. Which kind of store serves which access level? Today the domains live in Virtuoso, which enforces access levels itself: each level's account can only read the graphs that level may see (FR-AC-03, NFR-SEC-02). Faster or cheaper stores do not offer that:

      • QLever (C++, Apache 2.0) is a candidate to replace Virtuoso. It supports SPARQL 1.1 with named graphs, has its own text search (ql:contains-word), and builds its index in a separate step. It has no users or graph permissions: one access token only unlocks administrative calls, such as longer timeouts.
      • HDT is a compressed, read-only RDF file that can be queried without loading it into a database. Through hdt-jena (LGPL) SPieGeL could query it in-process, without a separate server; qEndpoint and Fuseki can serve it as an endpoint. HDT has no named graphs, and hdt-java was last released in 2023.
      • Oxigraph can serve a store it has loaded in a read-only mode.
      • Neo4j is not a SPARQL store and keeps named graphs only partly; it fits only as a public artefact built by the loading chain, for consumers (question 33).

      Access is restricted per triple, not per resource: a person's employment by a company can be public while the person's name is not. There are four ways to combine such stores with access levels:

      1. One cumulative store per level. Each level gets its own copy, with its own graphs and those of the levels below. Separation is physical and queries do not change, but public data is duplicated in every copy. For a large QLever index, every extra level is another full index to build and store.
      2. One file per level, combined per request. Each level gets its own HDT file, without overlap. SPieGeL builds a Jena union of the files the caller may see, so joins across levels still work. This only works in-process: with separate servers it becomes federation, which makes joins slow and complex.
      3. One store with named graphs, restricted by rewriting queries. Workable for SPieGeL's own queries, but risky for /sparql, where every FROM, FROM NAMED, GRAPH and SERVICE must be checked or rejected. One missed construct leaks data, so this is weaker than NFR-SEC-02 requires. Ruled out by ADR 0011: SPieGeL never rewrites queries, and a store without graph permissions serves one access level only.
      4. Split on authentication. Anonymous requests go to derived stores built only from public graphs: for example HDT for /doc and QLever for /sparql. Authenticated requests stay on Virtuoso with today's accounts. No security has to be rebuilt, and the derived stores hold nothing sensitive, which also limits the damage of a configuration error. For an authenticated /doc request, the description can be merged from the public store and a query on the non-public graphs alone, because each query already names its own data source (see Request flow).

      Option 4 fits when most data and traffic are public, and the non-public part is small. It moves the security boundary to the loading chain (question 15). The public export must start from an explicit allowlist of graphs, never from "everything except the non-public ones". A check, for example a SHACL shape or a query for forbidden predicates, must reject any artefact that contains non-public data. Personal data such as names then stays in Virtuoso alone (ADR 0018, NFR-PRIV-01), so a deletion request does not have to be traced through derived artefacts and their releases. Labels of linked resources follow the same rule: for anonymous callers they come from the public store only. If Elasticsearch ever returns (FR-DS-03), it needs a separate index per level rather than a level field and a filter, because suggestions, highlighting and aggregations can leak values.

      A static domain such as dba (question 6) can be served entirely from a snapshot. Open points: which domains hold non-public data at all (question 2), and whether SPieGeL needs a kind of data source other than a SPARQL endpoint, such as an HDT file read in-process (FR-DS-01 only covers endpoints). 30. How do resources and their event streams meet? Two points follow from ADR 0006. First, discovery: a resource needs a way to point to the stream that publishes it, for example a Link header or a triple, and a domain needs a way to list its streams, for example as a DCAT data service in its dataset description (FR-ES-01). Second, versions: LDES members are often version objects with IRIs of their own (dct:isVersionOf the resource). Should SPieGeL dereference those IRIs, and serve past states of a resource, or only the current state? 31. Does a federating query engine have a role on the consumer's side? Integration across domains and stores is left to consumers (ADR 0006). A query engine such as Comunica can query several SPARQL endpoints, files and streams in one query. Do we document or offer such a set-up, for example in the SPARQL editor (FR-SPARQL-03)? 32. Where is the convention for URIs in other distributions documented, and who owns it? ADR 0007 asks GIS layers, downloads and APIs to carry each thing's URI. They need a shared convention: the attribute name (a gml:id cannot hold a URI), and how a feature in OGC API Features links to it. Does that belong to the Flemish URI standard, to OSLO, or to the department's own GIS guidelines? And which layers come first, for example the river segments? 33. Does Neo4j have a role for certain use cases? Neo4j is a property graph database, queried with Cypher. As a store for SPieGeL itself it fits poorly, mostly for reasons already in the requirements:

      • It has no SPARQL. Data sources are SPARQL endpoints (FR-DS-01), queries are .rq files under version control (FR-RA-02), and every domain offers a public SPARQL 1.1 endpoint with the standard result formats (FR-SPARQL-01, FR-SPARQL-02). Neo4j could therefore never be a tenant's only store: /sparql still needs a triple store, so Neo4j would always come in addition to Virtuoso or QLever, never instead of them. A Neo4j adapter behind the data source port is possible in the hexagonal design, but tenants would then maintain their queries in two languages, which undermines the idea that a new kind of resource needs only configuration. The port also assumes RDF results (see question 14), so the adapter would have to translate property graph results back to RDF.
      • The data model does not map without loss. RDF reaches Neo4j through the neosemantics plugin (n10s). It imports and exports Turtle, N-Triples, JSON-LD, RDF/XML, TriG and N-Quads, and supports SHACL validation and simple inference. The weak points are what SPieGeL relies on:
        • Named graphs. N-Quads can be imported, but by default n10s keeps only the triple, not the graph IRI. An experimental procedure annotates nodes with their graph IRI, so that the same resource can become several nodes; according to the Neo4j community forum it is limited and not maintained. SPieGeL's access levels rest on named graphs (question 29).
        • Language tags, datatypes, blank nodes and Skolem IRIs. Choosing a label by language priority and showing datatypes (FR-HTML-10), stable Skolem IRIs (FR-URI-04) and nested blank nodes (FR-RA-04) have to be imitated in a property graph. n10s can approach this by configuration, but a lossless round trip RDF → Neo4j → RDF would have to be proven and kept under test, with no functional gain.
        • Support status. n10s is a Neo4j Labs project, not a supported product. It runs only on self-hosted Neo4j (Community and Enterprise), not on the Aura cloud service.
      • Access levels would need a new design. Today Virtuoso enforces the access levels with one read-only account per level, which can only read that level's graphs (NFR-SEC-02). Neo4j's fine-grained permissions on labels, relationship types and properties are, as far as we know, part of the commercial Enterprise edition only. The graph-based model would have to be translated into those permissions, and access is restricted per triple (question 29), which maps badly onto nodes and properties. That is a new security design with new risks, while question 29 leans towards an option that rebuilds no security.
      • Its strengths matter little to SPieGeL. Neo4j has full-text and vector indexes and is strong at traversals. But keyword search uses the data source's own full-text index (FR-SRCH-01), which Virtuoso and QLever have; hierarchies and collections (FR-HTML-05) work with SPARQL property paths; and a description is bounded to its subject (FR-RA-06), so deep traversals are not part of SPieGeL's core task. A vector index matters for LLM use cases such as GraphRAG, which are not in SPieGeL's scope (assisted query building is won't).

      Neo4j may still be worth investigating beside SPieGeL, for use cases where a property graph is stronger than SPARQL: graph algorithms (paths, centrality, communities, for example networks of companies, permits and sites), graph data science, visual exploration of a network, GraphRAG, or data that a source system already keeps in Neo4j. Ways to connect it, none of which makes Neo4j a SPieGeL store:

      1. Neo4j as a derived artefact of the loading chain. Like an HDT file or a QLever index in option 4 of question 29, the loading chain builds a Neo4j database from an allowlist of public graphs. A separate application uses it. SPieGeL does not change, the security boundary stays in the loading chain, and the URIs in the nodes link back to the subject pages (ADR 0007). This is a decision for the loading chain (question 15) and for a consumer application (ADR 0006, question 31), not for SPieGeL's choice of store.
      2. Neo4j as a source. A source system that already keeps its data in Neo4j exports it to RDF (with n10s), and the result is loaded into the triple store, like the materialised non-RDF sources of question 28.
      3. Neo4j read live as RDF. n10s can also return RDF from Cypher over HTTP (to be checked). A tenant could then read a description from Neo4j as RDF without a Cypher adapter in the core. This still needs a SPARQL store for /sparql, and queries in Cypher. It is the least attractive option, to keep only if a concrete use case needs live data from Neo4j.

      Open points: which use cases exist in the department, and whether one of them needs Neo4j rather than a SPARQL store with its own analysis tools. Partly answered by ADR 0008: Neo4j is not a data source for SPieGeL, and a public Neo4j database built by the loading chain remains possible for consumers. Option 3 is therefore ruled out unless a later ADR supersedes 0008. 34. How can applications with a language model (LLM) use the published data? Such applications, for example question answering or GraphRAG, are built on top of the published data, outside SPieGeL, like the consumers of ADR 0006. Three building blocks fit SPieGeL's design without changing it:

      1. Text to SPARQL. A language model translates a question into a SPARQL query on a domain's public /sparql endpoint (FR-SPARQL-01). The domain's description of its own structure gives the model the schema as context: its vocabularies (FR-URI-03), and the SHACL shapes and Data Cube structure definitions (qb:DataStructureDefinition) that several domains already define in advance, such as the cubes of imjv. Where none exist, the structure can be derived from the data itself (FR-HTML-15). A domain's example queries, which pair a question in plain language with its correct SPARQL (FR-SPARQL-04), are ready-made examples for the model. This is the RDF counterpart of Neo4j's Text2CypherRetriever.
      2. Vector search as an entry point. Embeddings of the labels and descriptions of resources are kept in a separate vector index, with the URI as key. A question finds a few URIs by vector search. From those URIs, the application fetches the description and the neighbours through SPieGeL (/doc/… in JSON-LD or Turtle) or through SPARQL. This is the pattern of Neo4j's VectorCypherRetriever, with URIs and SPARQL instead. Only the vector index is new; it is a derived artefact of the loading chain (question 15), like the Neo4j database of question 33.
      3. Sources in every answer. Every resource has a dereferenceable URI, so an answer can link to the subject pages it is based on. ADR 0007 already makes those pages the landing page for links from elsewhere. This makes answers explainable, which is an advantage over retrieval from plain text.

      Points of attention:

      • Access levels are the main risk. Access is restricted per triple, so a language model layer runs on public data only, at least at first: the public derived stores of option 4 of question 29. The vector index follows the same rule, or it can leak labels and values, for the same reason as an Elasticsearch index.
      • Costly queries. Generated queries on /sparql need the same protection as any other client: the bounded concurrency per data source (NFR-OPS-02) and rate limiting per client (NFR-OPS-08).
      • Languages. The embeddings must handle Dutch labels, and English ones where a domain offers them (question 27).

      Open points: whether the department wants such an application, who would build and run it, and whether SPieGeL itself should offer anything for it, such as assisted query building in the SPARQL editor (graded won't in the traceability matrix). 35. Which vocabulary describes the pages of a large property (FR-RA-07)? Two candidates: Answered by ADR 0015: Hydra, with pages of 100 by default ordered by IRI, a bounded count cached per data version, and lists addressed by query parameters on the subject's doc URI.

      • Hydra: a page is a hydra:PartialCollectionView of a hydra:Collection, with hydra:first, hydra:next and hydra:last, and optionally hydra:totalItems. Simple, widely known, and made for exactly this. The specification is a Community Group draft that has hardly moved in recent years.
      • TREE: pages are nodes linked by relations (tree:relation, tree:node). It is the basis of LDES, which Digitaal Vlaanderen and OSLO use, so a client that reads event streams (ADR 0006) already knows it. It is designed for fragmenting large collections by a value, such as time, and is heavier than needed for "the next 100 members".

      Recommendation: Hydra, because the pages of FR-RA-07 are plain, ordered lists and Hydra describes them directly. TREE remains the vocabulary for event streams. Open points: the default page size, whether pages show a total count (a COUNT is costly on a large store, so at most cached), and whether a page has its own URI under the resource or is a profile of it (FR-CN-03). 36. What are the predecessor's actual load and response times? The throughput target (NFR-PERF-04) is relative to the peak load per tenant, and the store choice (question 29) needs a baseline. From the predecessor's access logs: requests per second at peak, per domain and per kind of request (/doc, /sparql, front page), and the share of each media type. Its response times can be measured from outside with the measurement script and the same requests as on candidate stores. Partly answered on Performance and availability: a 48-minute sample of the predecessor's own log gives about one /doc request per second at a median of 4 s, with most of the time spent above the store. Two complete days of the umbrella domain's proxy log show low external traffic (a few thousand requests a day) and an availability of about 97 %. Still open: the same for the other domains and over several weeks (the log export stops at 10,000 rows, so counts per day, path and status are better aggregated in the central logging itself); response times measured from now on; and whether most of the predecessor's requests for algemeen come from inside, from other domains resolving labels. 41. Is JSON-LD from CONSTRUCT on /sparql compacted with the tenant's context? ADR 0017 frames and compacts descriptions. A CONSTRUCT or DESCRIBE result has no single subject, so the frame does not apply, but the tenant's context could still give it short keys and stable shapes. Without it, the result is plain JSON-LD with full IRIs, the same on every tenant. Compacting needs the whole result in memory, which the result limit bounds; JSON-LD is not streamed either way (see Request flow). A client that wants other keys can compact the result itself with its own context. 42. Where do the labels of resources of other domains come from? Data often links to resources of another tenant, such as a concept from a code list of algemeen on an IMJV page. FR-HTML-10 shows such a link by its label only if the domain's own store holds one; otherwise the IRI is shown. ADR 0021 does not cover this: these labels change with the other tenant's data, and that data has its own access levels. The options are: the loading chain copies the labels into each store that links to them (question 15); SPieGeL looks them up in the other tenant's data source, at the public level only, as a configured label source; one shared label store, fed by the loading chain; or the IRI as it is. The predecessor's logs suggest that resolving such labels causes much of its load on algemeen (question 36, Performance and availability).
